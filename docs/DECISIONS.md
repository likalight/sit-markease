# Decisions log

Deviations from `docs/PRD.md`, with a one-line rationale each. Newest first.

## Demo polish: rubric PDFs, faster mapping, and active-only insights

Rubric PDF/image extraction is now available directly on each question's rubric editor, not only during new-assignment creation. The import route reads the uploaded document, targets the existing question prompt, structures criteria, and returns them into the editable UI; it does not persist until the educator explicitly saves.

Whole-script mapping now skips Python CV preprocessing by default and uses a fast normalized page image for mapping/cropping, with the previous sidecar preprocessing available behind `AIMS_SCRIPT_PREPROCESS=true`. This keeps the demo responsive while preserving the original source pages for the side-by-side mapping/review view.

Insights now hides archived assessments, matching `/assignments`. The guarded demo configurator also shortens the visible assessment names to `Math` and `Physics`.

## Full-assessment delivery, private rosters, timers, and whole-script mapping

The demo now has one product flow per assessment mode instead of one upload per question. Assessments can be issued to a private student roster with opening/due times; formative assessments also have a server-authoritative duration and attempt allowance. Students start one assessment attempt and upload one PDF or several page images for the whole response. Summative intake uses the same whole-script shape, but the educator uploads on the student's behalf.

A new `S1c_question_map` structured vision stage maps normalized page regions to the assessment's real question UUIDs. It supports multiple questions on one page and one question continuing across pages. The mapping is persisted and rendered over the complete source pages; summative scripts always stop for educator confirmation before per-question grading, and low-confidence formative mappings stop there too. Confirmed regions are cropped/stitched into the existing per-question `submissions` pipeline so evidence citations, source-beside-transcription review, rubric grading, and audit behavior stay unchanged. The mapper is never allowed to invent a question ID, and ambiguous regions remain unassigned.

Summative approval and release are now distinct. Approving question results creates the existing audited `final_grades`, but students cannot see them until the educator explicitly releases the assessment, which writes a separate assessment-level audit event. Formative results retain the documented mode-gated immediate-release exception and are grouped by assessment attempt on the student feedback page.

The old demo rows are archived rather than deleted. `scripts/backup-demo-data.ts` exports the current domain data first; `scripts/configure-demo-assessments.ts` is guarded by `AIMS_CONFIGURE_DEMO=true` and leaves only the Maths summative and Physics formative papers visible while preserving the two existing graded Maths practice submissions.

## Gradescope-style app shell + rubric authoring/review + Cohort dashboard (E4/M10)

Three changes together, from direct instructor feedback on the live app:

- **Persistent left sidebar, replacing the top nav bar** (`src/components/app-sidebar.tsx`, `sidebar-nav-links.tsx`), same colors/fonts/spacing tokens, Gradescope's structural convention instead of ours. `NavHeader` is deleted (fully superseded); both `(student)` and `(educator)` layouts now share one fixed-height, sidebar+scrollable-content shell shape.
- **Rubric review/edit before opening for submissions** — previously a rubric was set once by AI at question-creation time with no way to change it short of the mid-review "+Add rubric item" (which needs a submission to already exist). New `replaceRubricCriteria` facade method (delete-then-reinsert, rubrics are small) backs a new `/assignments/:id/rubric` page; `new/actions.ts` now redirects there instead of straight to `/assignments`. The same page also gained "+ Add another question" (`/assignments/:id/questions/new`), closing a real gap: every multi-question assessment before this only existed via one-off scripts, since `/assignments/new` always created a brand-new assessment rather than appending to an existing one.
- **`/assignments` regrouped from one-row-per-question to one-row-per-assessment**, and rendered as a real `<table>` — a 7-question assessment used to render as 7 identical-titled rows (`db.listAllQuestions()` had no grouping). Also deleted one dead draft assessment (3 abandoned questions, superseded by a narrower replacement that was created instead of editing the original) that was inflating the same list.
- **Cohort dashboard, PRD's E4/M10** — specified in `docs/PRD.md` (heatmap/agreement/novel-candidates API routes, `(educator)/dashboard/`) but never built; `dashboard/` sat empty all session. Shipped a focused v1 instead, at `/insights`: score distribution, weakest rubric criteria (by avg `score/max_score` across the whole class, grouped by `criterion_key`), and top misconceptions — aggregate-only, no student names anywhere, per the PRD's explicit "not surveillance" framing. Agreement chart and novel-candidate queue deliberately deferred, not required for this pass.

## Practice-set generation reinstated for formative, not just summative

Reverses the "matching Nicholas's split... under closed-book/summative specifically" call below — explicit user direction this session was that a formative student should also be able to request a fresh practice set after a submission is graded, not only resubmit the same question. `feedback/page.tsx`'s action row now shows "Revise and resubmit →" whenever `c.isFormative`, and independently, the practice-set action (link if one exists, else `RequestRevisionButton`) for every card regardless of mode — the route, `s7-practice.ts`, and the practice page already had zero `assessment_mode` awareness, so this was a UI-only gate to remove, not a pipeline change.

## Four Gradescope-parity features added to the review console

Direct comparison against Gradescope's own rubric panel surfaced four real gaps in the review console: no manual point override independent of rubric clicks, no way to add a rubric item while grading (rubrics were only ever authored once, by AI, at question-creation time), no way to browse back to an already-approved submission, and no instructor-only note distinct from the student-facing feedback text. All four closed:

- **Manual point adjustment.** `review-console.tsx` gained an "Override total" control — a numeric field (seeded from the rubric-derived sum) plus a reason, independent of clicking through rubric levels one by one. On approve, the override becomes `totalScore`, `adjusted: true`, and the reason becomes `adjustment_note` — both fields already existed on `final_grades` for exactly this from the mode-safeguard work below; this was a UI gap, not a schema one.
- **"+ Add rubric item" mid-review.** New `POST /api/submissions/:id/criteria` — writes a real `rubric_criteria` row (shared by every submission of this question, same as an AI-authored one) plus a matching `criterion_results` row for the *current* submission's grade, tied to whichever step the instructor has selected (satisfies the schema's `evidence_step_indices` non-empty constraint, CLAUDE.md rule 4 — an instructor-added item still needs real evidence, not a placeholder). Deliberately minimal: a flat two-level scale (not-met/met), not a full AI-designed multi-level rubric — this is a quick "I noticed this, credit/dock it" tool, not a rubric-design surface.
- **Previous/Next navigation.** The page previously only computed a single forward `nextSubmissionId` from the review queue's ungraded-only grouping — which made sense for "Approve & next" but meant there was no way back to something already approved, since approving removes a submission from that queue entirely. Added a second, unfiltered batch (every submission for the question, ordered by `submitted_at`) that plain Previous/Next browse regardless of grade status, while Approve & next / Skip keep using the ungraded-only pair (renamed `nextUngradedSubmissionId`/added `prevUngradedSubmissionId`) — approving something correctly still advances to the next thing that actually needs a decision, not just the next submission chronologically.
- **Internal instructor note.** New `final_grades.internal_note` column (migration `0007`). Deliberately not added to the `feedback` table — that table is read directly by the student-facing feedback page, and CLAUDE.md rule 3's spirit (nothing reaches a student without deliberate release) argues against putting an internal-only field anywhere a `select("*")` on student-facing data could leak it. `final_grades` is never read by student-facing code, so it's the safe home for a note the student must never see.

Not built: rubric "Create Group"/"Import" (Gradescope's bulk rubric-authoring tools) — out of scope for a single-item mid-review add.

## Reintroduced educator-on-behalf-of upload — scoped to summative only

Self-submit (see "Real named assignments..." below) replaced the original educator-uploads-on-your-behalf flow on the reasoning that the educator's job is reviewing the uncertain queue, not doing intake for students. That's still right for formative practice, but it quietly assumed self-submit works for *every* mode — it doesn't for a real closed-book exam: the student hands in physical paper and never gets it back, so they can't photograph it themselves afterward. Only whoever collects the papers can attribute a script to a student.

Added `POST /api/questions/:id/submissions/educator` (educator-only, 403s for any other role) and `/assignments/:assessmentId/upload` (`EducatorUploadForm`) — an educator picks the question, types a student ID, attaches the file. The route 400s if the question's assessment isn't `assessment_mode: 'summative'`; formative stays self-submit-only, unchanged. Reuses the exact same `ingestSubmission` → `runFullPipeline` path the student route calls, just with the target student's uuid instead of the caller's — so a summative script uploaded this way lands in the review queue and behaves identically to a self-submitted one; nothing about the pipeline or approval gate changed.

Student identity: the login gate's 3-fixed-demo-ID → real-Supabase-account provisioning (`src/app/enter/actions.ts`) was extracted into `src/lib/auth/student-roster.ts` (`VALID_STUDENT_IDS`, `resolveStudentAccount`) so both entry points — a student logging in, or an educator typing that student's ID during upload — provision and resolve the identical account, rather than two copies of the same 3-ID list drifting apart.

Explicitly not built: true batch upload (many scripts in one action) and a real class roster beyond the 3 fixed demo IDs — this is one script, one student-ID lookup, per submission. Documented in docs/STUBS.md rather than silently scoped down.

## Formative vs. summative assessment modes — a scoped, mode-gated exception to rule 3

Nicholas's review pointed out that a single grading flow doesn't fit both a weekly low-stakes practice question and a real graded assessment — they need different release gates, different feedback styles, and different OCR-trust assumptions. Added `assessments.assessment_mode` (`'formative' | 'summative'`, migration `0006`, default `'summative'` — every existing assignment is unaffected). Named `assessment_mode`, not `mode` — a bare `mode` column collided with Postgres's `MODE() WITHIN GROUP` aggregate through PostgREST's query parser (`"WITHIN GROUP is required for ordered-set aggregate mode"` on a plain `select=mode`).

**This reintroduces a scoped version of the auto-release path removed in "Made the real pipeline match the pitch deck's 8-step journey" below** — that removal was correct for the general case (a blanket auto-release for every confident result genuinely violated CLAUDE.md rule 3), but formative/weekly-practice is a deliberately different product where instant feedback with no human reviewer in the loop is the entire point, not a bug. `orchestrator.ts`'s `autoReleaseIfFormative()` only fires when `assessment_mode === 'formative'`; every summative submission goes through the unchanged, unaffected instructor-approval gate.

Per-mode behavior:
- **Formative**: auto-releases immediately after S6 (`final_grades` row written with `approved_by: null`, `adjustment_note` naming it as such — never silent). Feedback tone is forced to `socratic` regardless of the student's stored preference (`feedback_tone`) — `prompts/s6_feedback.v2.md` now actually defines what "socratic" means (ask a guiding question pointing at the exact step, never state the mistake directly) where `v1` only had it as an unused enum value with no behavioral difference from `supportive`/`concise`. The student-facing feedback page shows the raw transcribed steps for formative submissions only (`OcrStepFlagButton`) so the student — the only safeguard, since there's no instructor gate — can flag a misread before trusting the grading; summative students still never see the transcription at all. "Request revision" is replaced with a direct "Revise and resubmit" link back to `/submit` (the practice-set-generation flow stays summative-only, matching Nicholas's split of "targeted follow-up practice" under closed-book/summative specifically). New `/assignments/[assessmentId]/attempts` page gives instructors/TAs the engagement visibility they lose by not having these in the review queue — attempt count per student, timestamps, scores, misread flags.
- **Summative**: unchanged — instructor-approval gate, full transcription hidden from students, confidence-based `needs_human_review` flagging into the review queue.

Also, separately: added an "instructor marking mode" section to the review console — the instructor previously verified the *score* but never saw the actual feedback text (`summary`/`next_action`) a student was about to receive; that text now renders in the review console itself, editable before approval (`PUT /api/submissions/:id/feedback`).

Not yet built: a formative assignment still needs its `assessment_mode` set at creation time (radio button on `/assignments/new`) — there's no UI to convert an existing assignment between modes after creation.

"Open for submissions" wasn't a real switch. (2) The landing page had drifted into generic template-feeling sections (a "why trust it" 3-card grid, generic subject tiles) instead of describing what the app actually does.

Deliberately did **not** reuse `s1-ingest.ts`'s `ingestSubmission()` — that function unconditionally creates a `submissions` row, which doesn't fit a reference-document upload. Paste-as-text stays as the alternative.

**Landing page rebuilt**, not edited: real 8-step journey with real tool names per step (replacing the generic sections), demo login (student 3-digit ID + educator one-click) embedded directly in the hero instead of linking out to a separate page. ## Made the real pipeline match the pitch deck's 8-step journey

Comparing the pitch deck's idealized journey against the actual code turned up four real gaps (not just deck-vs-docs ones — one of them was an actual violation of CLAUDE.md's own rule 3). All four fixed:

- **RAG in scoring.** `assessSubmission` (`src/lib/pipeline/s4-assess.ts`) never called `retrieveChunks` — RAG only existed in S7. Added `retrieveRubricReferences()`, mirroring S7's same corpus lookup (`db.listResources` → `db.listResourceChunks` → `retrieveChunks`), feeding retrieved worked-examples/misconception notes into `s4AssessUserPrompt` as background context — explicitly *not* authoritative over the rubric itself (`prompts/s4_assess.v2.md`). Bumped `PROMPT_VERSIONS.s4Assess` to `.v2`; `scripts/seed-ai-fixtures.ts` updated to call the same exported `retrieveRubricReferences()` so fixture cache keys match.
- **Removed the auto-release path.** `orchestrator.ts` used to write `final_grades` with `approved_by: null` whenever a result was confident — this directly violated CLAUDE.md rule 3 ("nothing writes final_grades without an explicit educator approval action"), something the original DECISIONS.md entry for it never actually flagged. Deleted that block entirely. Every result, confident or not, now waits in the review queue for a real `POST /api/submissions/:id/approve`.
- **Real "request revision" action.** S7 (practice generation) used to fire automatically inside the same orchestrator chain right after grading — no student action involved, despite the deck depicting one. Orchestrator no longer calls it; new `POST /api/submissions/:id/request-revision` (student-owned-submission check, requires a `final_grade` to already exist) triggers it instead, surfaced via a new "Request revision" button (`src/components/request-revision-button.tsx`) on the feedback page.
- **Split S7 into two real stages.** Generation and verification used to be one function logging one `stage_runs` row (`S7_practice`). Split into `generatePracticeItems` (logs `S7_practice`) and `verifyAndPersistPracticeSet` (logs `S7_verify`) in `src/lib/pipeline/s7-practice.ts`, with `generatePracticeSet` kept as a thin wrapper so existing call sites (the new request-revision route, seed-fixtures) don't need to change. No migration needed — `stage_runs.stage` is plain `text`, no enum/CHECK constraint.
- **Reskinned the review console + feedback page** to match the deck's dashboard mockup — added a `.review-theme` class in `globals.css` (same maroon/crimson/peach/cream palette and page-scoped Newsreader/Archivo/IBM Plex Mono fonts as `.landing-theme`, see the entry below), applied to `src/components/review-console.tsx` (ruled-paper backdrop behind the original-script pane, an "AI Summary" banner synthesized from the real recommendation data, a "Rubric — RAG-matched" eyebrow) and the student feedback page (the same AI Summary treatment around the real `feedback.summary` text, which is a genuine AI-authored sentence, not fabricated for the banner). Every other authenticated page (dashboard, insights, exam-prep, settings) is untouched.

## Added AWS Textract as a second, independent OCR hint alongside pix2text

Matches the pitch deck's step 2 ("pix2text + Textract" both feeding one AI reasoning step) more fully: `src/lib/ocr/textract.ts` calls `DetectDocumentText` (handles both printed and handwritten text — no need for the heavier `AnalyzeDocument` forms/tables mode) using the official `@aws-sdk/client-textract` SDK. Unlike the LLM providers in `src/lib/ai/`, this uses a real vendor SDK rather than raw fetch — Textract's auth is SigV4-signed requests, not a bearer token, and hand-rolling SigV4 would be a much bigger undertaking than the "no vendor SDK" convention was meant to avoid (that convention was about skipping heavy chat-completion SDKs when a bearer token + raw fetch suffices, not a blanket rule).

`readTranscription()` (`src/lib/pipeline/s2-transcribe.ts`) now calls pix2text and Textract in parallel via `Promise.allSettled`, each degrading independently — a missing `AIMS_AWS_*` config or a Textract API error just means one fewer hint, never a failed transcription (CLAUDE.md rule 8). `gatherOcrHintSources()` is exported specifically so `scripts/seed-ai-fixtures.ts` can build the identical hint text a live call would, keeping fixture cache keys in sync. Bumped `PROMPT_VERSIONS.s2Read` to `s2_read_single.v4` (generalised system-prompt wording for "one or two independent OCR passes" instead of just pix2text). The image is still the sole ground truth for both hints — same rule as pix2text alone.

Real Textract account: IAM user `aims-v2-textract`, `AmazonTextractFullAccess` policy, region `ap-southeast-1`. Code typechecks clean, but a real `DetectDocumentText` call against `eval/gold/images/correct.png` currently fails with AWS's `SubscriptionRequiredException` ("The AWS Access Key Id needs a subscription for the service") — an AWS-account-level gate (new account not yet fully activated / no verified payment method), not a code bug.

**Update — now live.** A payment method was added to the AWS account (`Billing → Payment methods`); after AWS's own account-verification lag cleared, the same `SubscriptionRequiredException` stopped occurring. Re-verified live against `eval/gold/images/correct.png` (the real handwritten script, not a synthetic one): `DetectDocumentText` returned 28 real `LINE` blocks with real confidence scores (0.62–1.00). Both `AIMS_AWS_*` and pix2text are now active OCR hints in `.env` — no further code changes were needed, exactly as designed when this was deferred.

Worth noting for future subjects: pix2text's math-formula-aware layer only earns its keep on genuinely symbolic work (ODEs, integrals, vector equations) — for subjects that are mostly handwritten prose or plain arithmetic (e.g. an accounting adjusting entry, an IV drip-rate calculation), Textract alone is a legitimate, sufficient choice on its own, no math-aware OCR needed.

## Added pix2text as an OCR pre-transcription hint for S2

The pitch deck's step 2 lists "Mathpix + Textract + RAG + OpenAI" as the tools behind AI reading & scoring, but the actual pipeline never used any OCR engine at all — S2 was a single OpenAI vision call doing raw reading and step-structuring together, with nothing to ground its self-reported confidence against. Added **pix2text** (github.com/breezedeus/pix2text), a self-hosted, open-source Mathpix-alternative, as a new sidecar endpoint (`sidecar/ocr.py`, `POST /ocr/transcribe`) that pre-transcribes the image line-by-line with its own confidence scores. `readTranscription()` (`src/lib/pipeline/s2-transcribe.ts`) now calls it before the existing vision call and folds the result into the prompt as a hint (`renderOcrHint()` in `src/lib/pipeline/prompts.ts`) — **not** a replacement: the image stays the final authority (CLAUDE.md rule 5), and a pix2text failure degrades to no hint rather than failing the stage (rule 8). Bumped `PROMPT_VERSIONS.s2Read` to `s2_read_single.v3` since the prompt content changed; `scripts/seed-ai-fixtures.ts` updated to call the same pix2text endpoint when seeding, so its cache key matches what a live call actually produces. No paid dependency added — pix2text runs fully locally, same as the existing OpenCV/SymPy/embeddings stages.

## Post-M9 — dropped the dual-vendor cross-read transcription design

`docs/PRD.md` §7.3 specified two independently-framed transcription reads from two different AI vendors, cross-checked for agreement, as the trust mechanism deciding auto-release vs. human review. On review, **the actual official brief the user was graded against never states this** — it names "multimodal LLMs" as a technology (plural, but not a requirement for cross-verification), not a two-independent-reads-must-agree mechanism. That design was elaborated into the PRD by an earlier session on top of the real brief, not handed down by it.

Given that, and given the real operational cost of running two vendors (Gemini's free tier caps at 20 requests/day — a hard wall hit during testing; Groq's open vision models read messy handwriting less reliably than proprietary ones, so a second read risked flagging correct work as disagreement rather than actually catching errors), the pipeline is now **single-model**: one multimodal LLM call (OpenAI) does literal transcription + step segmentation in one pass, reporting per-step confidence and overall legibility. Auto-release vs. human-review routing now uses that self-reported confidence plus S4's symbolic answer verification (unchanged) — CLAUDE.md rule 6 ("two systems must agree") is relaxed to "the read is confident and, where checkable, the answer verifies symbolically," which is still a real, degrade-never-crash trust gate, just not a cross-vendor one.

Changed: `src/lib/schemas/transcription.ts` (merged ReadA/ReadB into one `TranscriptionReadSchema`), `src/lib/pipeline/s2-transcribe.ts` (one `readTranscription()` call instead of `readA`+`readB`), `src/lib/pipeline/reconcile.ts` (renamed conceptually to quality assessment — `assessRead()` computes routing from confidence/legibility instead of cross-read agreement), `prompts/s2_read_single.v1.md` (merged prompt), `src/lib/ai/client.ts` (`fast` role now defaults to the same provider as `primary` — no more silent Gemini fallback), landing page + `journey-explorer.tsx` copy (no longer claims "two AI models"). `docs/PRD.md` itself is left as-is (historical planning doc); this entry is the record of the deviation from it.

## Post-M9 — three live-only bugs found by actually running the deployed app end to end

Every one of these was invisible in local dev and passed typecheck cleanly; only a real submission through the real Vercel deployment surfaced them.

- **Every AI-calling stage was silently crashing on Vercel.** `src/lib/ai/cache.ts`'s disk write ran unconditionally after every real model call, with no error handling. Vercel's serverless filesystem is read-only outside `/tmp`; the write threw `EROFS` *after* a successful, real, billed AI response, and since nothing caught it, the whole stage (and everything after it) was recorded as failed even though the model call itself had worked. Fixed by making both `aiCache.get` and `aiCache.set` best-effort (`try`/`catch`, cache-miss-or-skip on any filesystem error) — caching is an optimisation, never load-bearing.
- **The full S2-S7 pipeline reliably exceeded Vercel's default function timeout.** Seven-plus sequential real network calls (two transcription reads, reconcile, assess, diagnose, feedback, then practice generation with per-item verification) routinely run past a minute; the platform silently kills the function mid-pipeline with no exception ever reaching `stage_runs` — S7 in particular could show zero rows at all, not even a `failed` one, because the request was cut off before any of its own logging ran. Added `export const maxDuration = 300` to both routes that call `runFullPipeline` (`api/questions/[id]/submissions`, `api/submissions/[id]/process`).
- **`generatePracticeSet`'s own body (verification loop + the two DB writes) had no try/catch.** A throw there propagated all the way up uncaught, so a real, successful AI generation call (`callStructured`'s own success log for the `S7_practice` stage) could exist in `stage_runs` while no `practice_sets` row was ever created — indistinguishable from success unless you checked the DB directly. Wrapped the whole body; any failure now logs a real `S7_practice` failure row instead of vanishing. Also fixed `getPracticeSetForSubmission`, which used `.maybeSingle()` and discarded the error — if a submission ever ended up with 2+ practice_sets rows (itself caused by this same bug racing the idempotency guard), the lookup silently returned "not found" and the guard would create yet another duplicate. Now orders by `created_at` and takes the most recent.
- **Free-tier Gemini quota (20 requests/day) is a real, hard ceiling**, hit organically during this same round of live testing (`429 Too Many Requests`, `generate_content_free_tier_requests`). Not a bug — a genuine constraint of the free-tier `fast` role provider that will throttle real classroom usage almost immediately; a paid tier or a different `fast`-role provider is needed before any real cohort uses this.

The M2 pivot above was explicitly temporary. This entry records switching it off for real:

- **Product renamed Stepwise → Practica**, with a new icon-only mark (`src/components/logo.tsx`) and a full design-system replacement (black/white/red, matching the real SIT mark's geometry, replacing the earlier cream/soft-serif look). `AIMS` remains the formal project name (title, footer); Practica is the product.
- **Provider swap**: Groq (the `fast`-role dual-read partner) replaced with Gemini; OpenAI added as `primary`. Rationale: Groq's vision-model quality on handwriting was never validated, where OpenAI + Gemini are two genuinely capable, differently-trained vision models — cross-vendor agreement between *these* two is a real trust signal. `src/lib/ai/providers/openai.ts` uses raw `fetch`, no `openai` npm package, matching the existing Groq provider's style.
- **`AIMS_FIXTURE_MODE` and AI-live decisioning were incorrectly coupled.** The flag controlled both the DB/auth backend *and* whether an AI cache-miss attempted a real call. Flipping it to go live crashed every request (middleware tried to build a real Supabase client with no project configured). Split into two independent flags: `AIMS_FIXTURE_MODE` (DB/auth) and `AIMS_AI_LIVE` (AI cache-miss behavior) — see `src/lib/db/env.ts`.
- **Every stage's prompt was missing an explicit JSON shape in text.** All 6 AI-call sites (`src/lib/pipeline/prompts.ts`) said "respond with the JSON shape you were given" without ever actually giving one in the prompt text — the design relied entirely on Gemini's native `responseSchema` to constrain output. That silently worked in fixture mode (hand-authored fixtures already matched the schema) and broke immediately on real calls: Gemini didn't reliably honor the schema (returned markdown-fenced JSON with wrong field names) and OpenAI's JSON-object mode has nothing constraining it at all without an explicit shape. Fixed by appending a spelled-out shape to every user prompt, plus defensive markdown-fence stripping in both provider clients.
- **Real embeddings-based RAG.** `sentence-transformers` was listed in `sidecar/requirements.txt` but never actually installed (same class of gap as pdf2image below). Installed it; `src/lib/rag/retrieve.ts` now ranks by cosine similarity against real 384-dim vectors, falling back to the old keyword scorer only if an embedding call fails.
- **PDF support**, using `pypdfium2` instead of the originally-planned `pdf2image`: `pdf2image` needs the Poppler system binary, which isn't pip-installable and wasn't present. `pypdfium2` ships PDFium as a pure wheel, no external binary. Multi-page PDFs store every page but only grade page 1 — true multi-page transcription is a separate, larger change (concatenating multiple images into one dual-read call), not done here.
- **Real Supabase migration.** Schema (`supabase/migrations/0001_init.sql`, already written, unmodified) run against a real project; storage bucket created; real Supabase Auth wired for signup/login (previously a stub error); demo data re-seeded. Found and fixed several scripts (`ingest-corpus.ts`, `seed-gold-submissions.ts`, `seed-ai-fixtures.ts`, `eval/run.ts`) that bypassed the `db` facade and read `local-store`/`local-files` directly regardless of which mode was active — worked by accident while only fixture mode existed, broke immediately against Supabase.
- **Pipeline idempotency gap.** None of the S2/S4/S6/S7 stage functions guarded against being re-run on a submission that already completed that stage — the local JSON store silently allowed duplicate rows (`.findOne` just returns the first match), Supabase's `.maybeSingle()` correctly errors on 2+ matches instead. Surfaced as a real crash during fixture re-seeding; added an idempotency guard (return the existing result) to `transcribeSubmission`, `assessSubmission`, `generateFeedback`, `generatePracticeSet`. `diagnoseSubmission` inserts an array rather than reading with `.single()`, so it doesn't crash the same way, but a re-run still doubles up `misconception_tags` — not yet guarded.
- **`practice_attempts` wired up.** The table existed in the schema from the start but nothing ever read or wrote it — practice-page hints/attempts were pure client state, lost on refresh. Added `db.upsertPracticeAttempt`/`getPracticeAttempt`/`listPracticeAttemptsForItems` and a `PUT /api/practice-items/:id/attempt` route; `PracticeItemCard` now persists and restores per-student state, plus a self-reported correct/partial/incorrect outcome.
- **Auto-release / minimal educator-input model.** A confident, agreeing, symbolically-verified result now releases automatically (`src/lib/pipeline/orchestrator.ts`) with no educator action — the review queue already filtered to "no final_grade yet," so this alone was enough to make "the educator only sees the uncertain ones" literally true, not just a pitch claim.

## M2 — local JSON store + fixture-mode auth replace Supabase for M2 onward

No Supabase project and no Anthropic API key are configured in this build environment (flagged to the user after M0/M1; confirmed again here). The user chose: build against a local, file-backed mock store and fixture AI responses so the pipeline is actually runnable and testable now, rather than writing seven milestones of code against credentials that don't exist.

Concretely:
- `src/lib/db/local-store.ts` — a singleton JSON-file-backed store (`local-data/store.json`, gitignored) with the same entities as the §9 Postgres schema (submissions, transcriptions, solution_steps, grade_recommendations, criterion_results, misconceptions, misconception_tags, feedback, resources, resource_chunks, practice_sets, practice_items, stage_runs, plus modules/questions/rubrics/users for seed data). This is what M2 onward reads and writes.
- `src/lib/storage/local-files.ts` — original/processed submission images go to `local-data/uploads/<submissionId>/` instead of a Supabase Storage bucket.
- Auth: when `AIMS_FIXTURE_MODE=true`, login is a plain role-switch (no password) that sets a plain (unsigned — local dev only, never for a real deployment) cookie identifying the demo educator or student — no Supabase Auth call. `AIMS_FIXTURE_MODE=false` keeps the original Supabase Auth path from M0 untouched.
- M1's upload route and setup page were updated to branch on `AIMS_FIXTURE_MODE` and use the local store/files when true.
- AI calls (S2, S4, S5, S6, S7) go through `src/lib/ai/client.ts`, which in fixture mode returns hand-authored fixture JSON (validated against the same Zod schemas a real response would be) instead of calling Anthropic, and logs `cost_usd: 0` on the `stage_runs` row.

**This is explicitly temporary.** The Supabase migration, schema, and M0/M1 Supabase-backed code are left in place and are the intended production path — `docs/STUBS.md` tracks exactly what needs to happen to swap back (point `AIMS_FIXTURE_MODE=false` at a real Supabase project + `ANTHROPIC_API_KEY`, verify the local-store shapes still match the SQL schema, re-run each milestone's acceptance check against the real backend).

## M2 — 3 synthetic gold-set scripts instead of 20-30 real handwritten ones

§15 wants 20-30 real handwritten scripts, human-marked before anyone sees AI output. This build has neither real students nor a human marker, and — per the M2 pivot above — no live model access to grade real scripts against anyway. Substituted 3 synthetic, programmatically-rendered scripts (`eval/gold/images/*.png`, generated via `cv2.putText`, not real handwriting) for the seeded ODE question, each targeting a specific outcome: `correct` (full marks, no misconceptions), `dropped_c` (drops the constant of integration, patches the final answer anyway — correct answer, unsound method), `ic_too_early` (applies the initial condition before the general solution — much lower score). Each has a hand-authored "human mark" in `eval/gold/*.json` standing in for real independent human marking, and hand-authored AI-response fixtures seeded into `local-data/ai-cache/` (`scripts/seed-ai-fixtures.ts`) standing in for real model output.

This is a real reduction in what M9's eval harness can honestly claim: 3 synthetic scripts is not statistically meaningful and the "human marks" are the same person (this build) who wrote the fixtures, not an independent marker — M9's report says this plainly rather than presenting it as real accuracy data. The pipeline logic itself (reconciliation routing, rubric scoring, misconception tagging, feedback, practice generation) is exercised for real against these fixtures — what's synthetic is the input data and the "ground truth," not the code path.

## M2 — dropped the `server-only` import guard

`import "server-only"` throws unconditionally when a module is loaded outside Next.js's webpack/turbopack bundling (its conditional-exports trick only resolves under a bundler condition those tools define) — which breaks every standalone script (`scripts/seed.ts`, `scripts/ingest-corpus.ts`, `eval/run.ts`) that needs to import `local-store.ts`, `facade.ts`, the AI client, etc. via `tsx`. Removed the guard from the affected files. None of them are imported from a `"use client"` component (verified by grep), so the actual protection it gave was redundant with Next's module graph; the marginal safety net wasn't worth breaking every script.

## M0 — no RLS policies

The §9 schema is created with Row Level Security left off (Supabase default for freshly created tables). All reads/writes route through Next.js Route Handlers using the service-role client (`src/lib/db/supabase-admin.ts`), which is never imported into client code. Role/ownership checks happen in the route handlers themselves. Faster to build for a 36-hour hackathon; would need real RLS policies (or at minimum enabling it with matching policies) before any non-demo deployment.
